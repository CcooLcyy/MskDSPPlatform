# 平台 Docker 发布与更新方案

## 目标与范围

平台基础版本从 `0.0.1` 开始。提供 Linux amd64 Docker 镜像、可通过
`docker load` 导入的压缩镜像包、docker run 部署脚本、版本清单与 SHA256 校验文件。
当前 CI 由 GitLab 构建并上传至平台私有软件库，管理员决定是否安装；Stable
保留已有远程发布流程，不创建对应分支或正式标签。本方案说明构建和更新边界，
点表库及认证能力以各自功能文档为准。

## 平台入库与单容器网页更新

一个容器内运行常驻 Python 管理进程与 Rust 平台子进程。
管理进程提供更新接口并代理 HTTP，Rust 继续独立提供 gRPC。公开 HTTP 为 8080，
Rust 内部 HTTP 为回环 8081，gRPC 为 50000。页面通过“检查更新”“更新到最新版”
发起更新；加载页面与轮询仅读取状态，不定时检查或安装，不安装宿主机服务。

GitLab CI 通过带专用令牌的 gRPC 上传接口提交程序包，完整入库后形成私有候选包，
不调用发布或安装接口。平台检查本地软件库，管理员选择升级；CI 不再更新 R2 清单。
程序包根成员唯一且名为 `mskdsp-platform`，项目、通道、平台、版本、完整提交、
大小与 SHA256 均需校验。镜像归档和可选离线交付包保留在 GitLab 作业产物中。

Stable 仍支持 R2 的 `mskdsp-platform/stable/latest.json`，
各版本包含同源镜像包和二进制包。资产先上传并公开校验，最后更新入口；正式版本
不允许不同内容覆盖。旧资产只在入口和保留对象验证成功后，按当前项目/通道精确清理。
历史 `ci/latest.json` 不再作为当前 CI 的更新来源。Beta 新包、发布工作流和远程更新源已退役，已有分支、标签和包保持不变；历史版本读取与软件仓库旧包查询、下载、撤回继续兼容。

更新器只读取只读 `updater.json` 中的固定更新源；CI 默认为
`{"source":"platform","channel":"ci"}`，Stable 可显式配置远程来源。
网页不接受 URL、命令或文件路径。候选二进制校验版本身份后才切换；准备阶段旧程序继续服务。切换会短暂停止平台
子进程并断开 gRPC 长连接，客户端需要重连。HTTP 版本、就绪接口和真实 gRPC
握手验证成功后才原子提交状态；失败恢复本地上一版，并报告回滚结果。
配置保持只读挂载，程序版本与安装状态保存在持久化 runtime 卷；重启以最后成功
提交的版本恢复，不能被基础镜像种子覆盖。基础镜像、管理器及系统库升级需单独维护。

默认部署使用 `docker run`，Compose 仅保留可选模板。宿主机工作目录统一为 `/home/daniel/mskplt`，配置、运行状态、更新程序、业务数据、日志和临时文件按 [平台工作目录](平台工作目录.md) 保存在该目录内。宿主机端口默认仅回环暴露，
管理页面可通过受保护的网关或 SSH 隧道访问。动作头和 Origin 校验用于限制跨源
浏览器请求，不替代管理员登录认证。运行端无需 R2 写入凭据或 Docker Socket。

新增验收包括：清单与包异常拒绝、版本倒退/冲突、重复更新互斥、成功提交、失败回滚、
掉电/重启恢复、子进程回收、有界重启，以及页面检查/安装按钮与轮询契约。

## 通道与版本

| 通道 | 自动触发 | 手动触发 | 滚动镜像标签 | 交付入口 |
| --- | --- | --- | --- | --- |
| CI | GitLab 推送 `main` | 在 main 运行 GitLab 流水线 | 不推送 | 平台私有候选包、GitLab 产物 |
| Stable | 推送 `vX.Y.Z` | 指定已存在的正式标签 | `stable`、`latest` | `vX.Y.Z` 正式发布 |

PR 仅运行检查，不发布。`Cargo.toml` 和 `Cargo.lock` 的自有包版本必须一致。
CI 使用基础版本加通道、UTC 时间、工作流运行编号和提交短号构成版本；
Docker 标签将 SemVer 中的 `+` 替换成 `-`。Stable 版本必须与正式标签完全一致，
并且提交必须位于远端 main 或匹配版本的 release/X.Y 历史中；远端标签解引用提交必须等于冻结提交。

## 构建、验证与发布顺序

1. 校验发布来源，捕获完整提交 SHA；后续步骤使用相同代码，避免分支移动导致版本漂移。
2. 运行发布工具单元测试、Rust 格式检查和已有 Rust 测试。
3. 构建非 root 镜像；容器运行和程序更新恢复烟测由人工按需执行，不进入自动发布流程。
4. 检查 Docker 包内的标签和镜像配置摘要，生成程序包、压缩镜像包和上传元数据。
5. CI 确认构建提交仍为远端 main 最新提交，再上传平台并确认完整入库；可选离线包由手动作业生成。
6. Stable 生成部署配置、清单及校验和，发布 R2、GHCR 和 GitHub Release；每次对外发布前校验远端正式标签及允许的分支历史。

同一通道串行上传或发布。GitLab CI 使用只允许平台 CI 入库的专用令牌。Stable
工作流使用仓库自动提供的 `GITHUB_TOKEN`，仅发布作业获得
`contents: write`、`packages: write`，不需要外部镜像库密码。
GHCR 新建包的可见性需在 Packages 设置中核对；公开 Release 离线包可独立使用。

## 验收标准

- `0.0.1` 为唯一基础版本来源；无效版本、错误分支、错误标签、来源不属于远端 main 或匹配版本 release/X.Y 历史、标签缺失或移动均被拒绝。
- CI 构建与平台入库成功，程序包和镜像包保留 GitLab 产物；手动离线作业生成启动脚本、配置、清单和 SHA256；Stable 不自动首发。
- 容器监听内部 `0.0.0.0:8080/50000`，部署默认仅映射宿主机 loopback。
- `/api/v1/version` 可核对构建版本、通道、完整提交和构建时间。
- 镜像包可以导入，包内镜像 ID 与清单一致，下载文件校验和与发布记录一致。
- 上传成功不触发安装或重启，候选包等待管理员检查并选择升级。
- 发布通道标识构建来源，业务功能仍需独立验收；当前服务未提供原生 TLS。
