# 隧道上传阻塞诊断与恢复验证

## 目标与边界

现场安装包上传约 2 MiB 后遇到“隧道响应阻塞超时”，随后控制连接心跳超时。
目前只能确认平台的有界响应队列连续 30 秒无法继续入队，不能据此认定共享 gRPC
连接是根因。现有 relay 两个方向已经并行运行，本次保留队列容量、超时和接口。

输入仍是已完成鉴权和附着的 TunnelFrame 双向流，输出保持数据、半关闭和错误语义。
本次仅补充诊断与回归保护，不记录 SSH 内容、安装包数据、票据或认证信息。

## 方案

- 每个方向独立累计成功入队的数据字节及帧数，入队前的数据不能计为已转发。
- 数据面开始时记录隧道 ID、方向和队列容量；每累计 2 MiB 输出一次进展。
- 入队失败时记录隧道 ID、方向、累计成功字节、当前帧字节、等待毫秒、
  队列剩余容量及距最近成功入队的毫秒数；阻塞超时错误携带方向和累计字节。
- 每个方向退出时输出累计量和耗时；取消或另一方向先失败而丢弃 pump 时也输出摘要。
- 方向摘要与现有外层隧道、控制连接日志通过隧道 ID 关联；不输出远端负载。
- 仅在失败测试证明现有清理有缺陷时修改恢复路径，保持单隧道失败不取消设备控制连接。

## 异常与验收

1. 满队列超时：累计成功字节不增加，错误明确方向和既有成功字节。
2. 接收端关闭或控制取消：退出及时，方向摘要仍然输出。
3. 本机真实 TCP 服务经 localhost gRPC 收到并回写 50 MiB 二进制，半关闭后尾部完整。
4. 上传方向持续背压时，反方向数据和设备控制 HeartbeatAck 仍可到达。
5. 取消背压隧道后，Hub 隧道表清空，控制连接仍在线，能重新开隧道并交换数据。

按“方案 -> 新增测试 -> 实现 -> 回归”执行。本地工具链不可用时保留具体错误，
由 GitLab 的 cargo fmt、build、test 门禁编译和执行；本次不部署、不进行远端构建。
