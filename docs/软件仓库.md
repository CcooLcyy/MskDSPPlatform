# 软件仓库

## 目标与边界

平台接收 CI 或发布客户端通过 gRPC 上传的上位机、下位机和测试上位机安装包，以及独立的测试用例 ZIP。各产品分别保存历史版本和 CI、Stable 通道推荐，客户端通过公共 gRPC 目录查询并流式下载。
上下位机部分实现协议、平台服务及管理页面；上位机客户端接入与真实部署需分别验收。
平台自身另有 [CI 入库与手动更新](平台自身CI更新.md)：只上传并完成入库，不发布到公共目录；管理员显式决定升级。

## 持久化

复用平台业务数据根目录，在其下建立 software/software.sqlite3、software/uploads/<上传ID>/package.part 和 software/packages/<产品>/<版本>/<架构>/<文件名>。
默认容器目录是 /var/lib/mskdsp-platform/data/software，对应宿主机 /home/daniel/mskplt/runtime/data/software。
文件名、产品、版本、架构必须校验；客户端不能指定服务器路径。安装包在文件系统保存，数据库保存元数据、上传任务和通道指向。

## 协议与状态

平台协议定义放入 MskDSPPlatformProto，由 platform-proto 子模块构建；保留现有 Agent 协议。
SoftwarePublishService 提供 CreateUpload、UploadPackage（客户端流）、GetUpload、CompleteUpload、PublishRelease、WithdrawRelease；SoftwareCatalogService 提供 ListPackages、GetPackage、DownloadPackage（服务端流）。
发布接口使用 authorization: Bearer <高熵令牌>，服务器仅配置令牌 SHA256。未配置时发布接口关闭，不影响平台其他功能。

公开软件包产品为 `mskdsp-upper`、`mskdsp-lower`、`mskdsp-testbench` 和 `mskdsp-testbench-cases`。元数据包含 version、platform、file_name、size、sha256、signature、notes、package_version、image_id、source_repository、source_ref、source_sha。
上位机平台沿用 Tauri 的 windows-x86_64-nsis/windows-x86_64 等目标名，必须提供签名。下位机支持 linux-arm64/linux-x64，必须包含 package_version 和 sha256 镜像 image_id。
测试上位机使用 `mskdsp-testbench`、`windows-x86_64-nsis` 和 Tauri 更新签名原文。CI 上传须显式填写 `channel=ci`，支持 `x.y.z-ci.<17 位北京时间戳>`，例如 `0.1.1-ci.20261110143025123`。平台也接受现有的 `x.y.z-ci.<构建编号>.<尝试编号>`，其中两个编号均为正整数。新增 Stable 安装包版本为 `x.y.z`，上传元数据的 `channel` 可传 `stable` 或留空。历史 Stable 包继续按 Stable 处理。发布和撤回请求须显式指定安装包所属通道。已有 CI 推荐时，旧版本不能替换新版本。
测试用例包使用 `mskdsp-testbench-cases`、`python-zip` 和 `mskdsp-testbench-cases_<version>.zip`，`source_sha` 填写 40 位小写十六进制提交 ID，`signature` 填写 Tauri signer 生成的独立用例包签名。上传、发布和撤回均显式指定 `ci` 或 `stable`。Stable 版本使用 `x.y.z`，CI 版本使用 `x.y.z-ci.<构建编号>.<尝试编号>`，两个编号均为正整数。CI 推荐仅能切换到同一或更新版本，Stable 可重新推荐历史版本。
同一产品/版本/架构不可用不同内容覆盖；相同元数据重复创建任务可返回已存在任务或已完成结果。

任务状态：uploading（可按已接收偏移继续）、completed（校验入库）、failed（校验失败）、expired（过期清理）。
每块携带上传 ID 和从零开始的 offset，大小上限 1 MiB；单包上限可配置但不超过 8 GiB。最多 32 个未完成上传任务，拒绝超长、越界、错误偏移、重复/缺失身份。
流结束只记录已接收进度，不代表入库；CompleteUpload 独立校验实际大小和 SHA256，再将文件移入正式目录。完整性失败不创建可发布包，任务失败不可继续。
写文件与数据库跨介质不是单一事务：启动和重复完成请求必须可恢复，正式包不可被覆盖或公开半成品；发布前再次确认包存在且大小/摘要正确。
未完成上传 24 小时未活动后过期并清理临时文件，重启后继续按已落盘偏移查询和续传。

## 发布与清单

已确认的通道预期：上下位机停止新增 Beta 发布，管理页只提供 CI/Stable 发布选择、筛选与推荐摘要。历史 Beta 记录仍显示原通道标记，保留查询、清单、下载和撤回；管理页通过独立的“撤回历史 Beta”操作停止旧通道推荐，不提供重新发布 Beta。现有数据库和协议字符串字段无需迁移。
上下位机入库及 Stable 发布不要求来自 Beta 或 main；允许发布客户端上传 main 或 release/X.Y 来源的正式补丁包，来源门禁由对应产品发布流水线负责。平台自身仍只接收 main 的私有 CI 候选包；平台自身 GitHub 发布现已退役 Beta，仅保留 Stable，来源校验见 [发布方案](发布方案.md)。

回归验收：后端拒绝新增及重复 Beta 发布，失败不改变 CI/Stable 或历史 Beta 引用；重启后历史 Beta 仍可查、下载及撤回，撤回不删除文件。上下位机 release/X.Y 来源包仍可发布 Stable。页面不再提供 Beta 发布/筛选/推荐，保留历史标识、下载及独立撤回入口。先编写回归用例，再实现；本次不在本地执行构建或测试，由提交对应 CI 验证，旧的本地验证记录不代表本次结果。

上传完成只进入待发布版本库，发布是单独动作。通道指向按产品/通道/架构保存；下位机 x64 仅允许 CI。
发布操作校验版本文件后事务更新通道指向，失败保留原指向。发布同一包幂等。切回历史包使用同一发布接口，并遵循各通道的版本限制。撤回只删除仍指向指定包的通道引用，不自动选取另一个版本，不删除历史文件。
上位机同一通道各架构必须属于同一版本，升级版本时原子切换版本并避免新旧版本混入一份清单；相同版本的新架构可以合并。
清单从数据库动态生成并返回 Cache-Control: no-store，不维护可能与数据库不一致的实体 latest.json。

HTTP 路由：
- /mskdsp-upper/<通道>/latest.json：Tauri version/notes/pub_date/platforms（含 url/signature）。
- /mskdsp-testbench/<通道>/latest.json：支持 `ci` 和 `stable`，提供 `version`、`notes`、`pub_date` 和 `platforms.windows-x86_64-nsis` 下的 `url`、`signature`。暂无推荐版本时返回 HTTP 204。
- /mskdsp-lower/<通道>/latest.json：linux-arm64 的现有 schema_version=1 清单。
- /mskdsp-lower-x64/ci/latest.json：linux-x64 清单。
- /software/packages/<包ID>/<文件名>：正式安装包下载，支持 HEAD 和单区间 Range。
- /software/packages/<包ID>/SHA256SUMS：下位机清单关联校验文件。

下载 URL 使用配置 software.public_base_url（允许显式 HTTP 内网测试，生产使用 HTTPS），不能从未验证的 Host 或转发头生成。测试上位机和测试用例包通过 gRPC 查询和下载，可在未配置该地址时发布。客户端查询用例包推荐时传入 `product=mskdsp-testbench-cases`、`platform=python-zip` 和目标 `channel`，再使用返回的包 ID 调用 `DownloadPackage`。
公开清单和下载不要求管理员 cookie，避免后台更新被登录页面阻断；只公开已发布或曾发布过的完整包，不公开上传临时文件和待发布包。

gRPC 客户端使用 `DownloadPackage(package_id, offset)` 下载上述同一公开安装包，不依赖 HTTP 下载 URL。每块最多 256 KiB，携带连续偏移、完整大小/SHA256，只有末块 `eof=true`；文件尾偏移返回空 EOF，越界返回 `OUT_OF_RANGE`。平台在同一文件句柄上分块预校验大小和 SHA256 后发送，客户端完成后仍必须核对整包和产品签名。公开边界、取消、超时和测试方案见 [gRPC 软件下载](gRPC软件下载.md)。

## 配置与接入

在平台配置文件增加以下配置（旧配置缺省兼容，默认不允许机器发布）：

```toml
[software]
public_base_url = "https://你的平台域名"
publisher_token_sha256 = "替换为发布令牌的64位十六进制SHA256"
testbench_publisher_token_sha256 = "替换为测试上位机 Stable 令牌的64位十六进制SHA256"
testbench_ci_publisher_token_sha256 = "替换为测试上位机 CI 令牌的64位十六进制SHA256"
testbench_cases_publisher_token_sha256 = "替换为测试用例包 Stable 令牌的64位十六进制SHA256"
testbench_cases_ci_publisher_token_sha256 = "替换为测试用例包 CI 令牌的64位十六进制SHA256"
max_package_bytes = 8589934592
upload_retention_seconds = 86400
```

发布令牌应使用密码学随机源生成至少 32 字节，原文仅交给发布端安全保存；平台配置保存原文的 SHA256。
令牌原文保存在发布流水线的机密变量中。空摘要关闭对应令牌，配置示例默认不含有效凭据。
测试上位机的两个 gRPC 令牌各自只可上传、续传、完成入库、发布及撤回对应通道的安装包。两个令牌须分别配置，也须与 `publisher_token_sha256` 和 `ci_upload_token_sha256` 区分。平台管理员可在软件管理页按安装包所属通道发布或撤回，并查看 CI 和 Stable 的独立推荐。
测试用例包的两个令牌各自限本产品的对应通道，也须与其他软件上传和发布令牌分别配置。管理员可在软件管理页的「测试用例包」分区发布、撤回和回退 Stable。
管理页面发布使用管理员会话，不借用发布令牌；公开目录只列已发布或曾发布的包。
对外部署使用支持 HTTP/2 的 TLS 网关代理 gRPC，平台目前的原生 gRPC 监听仍为内部明文；gRPC 流数据必须原样透传，代理消息上限至少覆盖 1 MiB 分块及少量元数据。
测试上位机的 GitHub Actions 和安装版共用平台原生明文 gRPC 入口。发布作业使用对应通道的 Bearer 令牌上传和发布，客户端通过公共 gRPC 目录按通道查询、下载安装包并验证签名。测试上位机的 HTTP 更新清单需要配置 `software.public_base_url` 才能生成下载地址。

CI 或发布客户端从协议仓库生成客户端代码后，依次调用 CreateUpload → GetUpload/UploadPackage → CompleteUpload → PublishRelease。
每条分块消息均携带同一 upload_id、当前 offset 和数据；上传流中断先查询实际偏移，再续传。完整性失败的任务需要重新创建。
客户端流正常结束不等于入库，更不等于发布。发布请求响应丢失时可重复同一请求，并通过目录或 latest.json 验证通道。
`signature` 保留发布者提供的 Tauri 签名字符串，`image_id` 是发布者提供的镜像配置摘要。平台验证元数据格式和文件大小、SHA256，测试上位机使用独立用例包公钥验签。

## 构建、部署与恢复

平台必须检出父仓库固定的协议提交才能编译。可运行 `python script/init_platform_proto.py`，不会自动升级协议版本。
协议子模块已迁至 GitHub 公开仓库，CI 无需 `PLATFORM_PROTO_READ_TOKEN`。初始化脚本先同步 `.gitmodules` 中的地址，再按父仓库固定提交检出，不向 GitHub 传递旧 GitLab 读取令牌。
执行构建的机器必须能访问 GitHub；此协议依赖不再要求内网 GitLab 连通性。本次没有改动服务器网络或运行远端发布。
Docker 构建上下文包含协议文件，但排除子模块 `.git`；运行镜像不携带源仓库或上传端凭据。

软件仓库按单写平台实例运行，不支持多个进程并发写同一个上传任务；同实例多 RPC 使用统一存储锁串行处理，大包复算摘要期间查询和其他上传可能等待。
维护任务启动时及每小时清理超过配置保留时间的失败/未完成上传，不清理正式版本包。临时文件丢失或入库中断时逐任务恢复，不能把未知文件当成已发布包。
备份时停止平台子进程后复制整个 `software/` 目录，包含数据库、可能存在的 SQLite WAL/SHM 和安装包；恢复也应使用同一份完整备份，不能仅复制数据库或包目录。
撤回只移除清单引用，曾发布文件仍可通过固定 URL 下载；如需彻底下架或删除历史文件，应另行定义保留和撤销策略。
